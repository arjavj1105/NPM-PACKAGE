# express-response-cache

A lightweight, zero-dependency in-memory response caching and automatic invalidation middleware for Express.js applications.

Designed to eliminate redundant database queries and API calls by transparently caching eligible `GET` responses with configurable time-to-live (TTL) expiration, while automatically invalidating affected cache entries when successful mutations (`POST`, `PUT`, `PATCH`, `DELETE`) modify application resources.

---

## Features

- **GET Response Caching**: Seamlessly caches successful HTTP 2xx responses while bypassing non-GET methods and error responses (4xx/5xx).
- **Default 60-Second TTL**: Sensible 60-second expiration out of the box, with simple per-route or global customization.
- **Automatic Cache Invalidation**: Automatically clears related cached responses following successful mutation requests (`POST`, `PUT`, `PATCH`, `DELETE`).
- **Resource Tagging System**: Group cache entries under logical resource tags (e.g., `'products'`, `'product:1'`) for targeted, granular invalidation without clearing unrelated caches.
- **In-Memory Storage**: High-performance key-value store with sub-millisecond lookups and secondary tag indexing (`O(1)` access).
- **Intelligent Query Normalization**: Eliminates cache misses caused by differing query parameter orders (e.g., `?sort=asc&limit=10` and `?limit=10&sort=asc` share the same cache key).
- **Header Preservation**: Safely preserves application headers (e.g., `Content-Type`, `Cache-Control`, `ETag`, and custom app headers) across cache hits while excluding transient transport headers.
- **Cache Status Headers**: Inspect responses with `X-Cache: HIT` or `X-Cache: MISS` alongside `X-Cache-Timestamp`.
- **Public & Internal Metadata API**: Inspect timestamps (`createdAt`, `expiresAt`, `ttl`), tags, and programmatic invalidation (`invalidateByTag`, `invalidateTags`).
- **Zero Runtime Dependencies**: Uses Node.js standard library primitives (`Map`, `Set`, `URLSearchParams`, `setInterval`), keeping your production bundle footprint minimal.

## Quick-Start Example

```javascript
const express = require('express');
const cache = require('express-response-cache');

const app = express();

// 1. Cache GET requests for 60 seconds (default TTL)
app.get('/api/users', cache(), (req, res) => {
  res.json([{ id: 1, name: 'Alice' }]);
});

// 2. Cache with custom TTL (e.g., 30 seconds)
app.get('/api/stats', cache({ ttl: 30 }), (req, res) => {
  res.json({ activeUsers: 42 });
});

app.listen(3000, () => console.log('Server running on http://localhost:3000'));
```

## Cache Status Headers

The caching middleware automatically injects diagnostic HTTP response headers:

- `X-Cache: MISS` — The response was generated by the downstream route handler and stored in cache.
- `X-Cache: HIT` — The response was served directly from in-memory cache without hitting controllers or database services.
- `X-Cache-Timestamp` — ISO-8601 timestamp representing when the response was captured and stored.

## Custom Key Generation

By default, cache keys follow the canonical format: `<METHOD>:<PATH><SORTED_QUERY>`.  
For instance, `/products?b=2&a=1` is normalized to `GET:/products?a=1&b=2`.

You can customize cache key generation using the `keyGenerator` function:

```javascript
// Example: Cache per authenticated tenant header
const customKeyGen = (req) => {
  const tenant = req.headers['x-tenant-id'] || 'public';
  return `${tenant}:${req.originalUrl}`;
};

app.get('/api/dashboard', cache({ keyGenerator: customKeyGen }), handler);
```

## Resource Tags & Automatic Invalidation

### What is Cache Invalidation?
When client applications perform write operations (mutations like creating, updating, or deleting data), previously cached GET responses become **stale**. Automatic cache invalidation ensures that as soon as a mutation succeeds, the outdated cached responses are purged so subsequent reads fetch fresh data immediately.

### How Resource Tags Work
Instead of hardcoding endpoint paths, `express-response-cache` uses **Resource Tags**:
1. When caching a `GET` route, you attach one or more tags (static string, array of strings, or dynamic resolver function).
2. When configuring a mutation route (`POST`, `PUT`, `PATCH`, `DELETE`), you specify which tags should be invalidated upon success.
3. When the mutation completes with an HTTP 2xx status, all cache entries associated with those tags are evicted.

### Precision & Resource Isolation
- Creating a product (`POST /products`) invalidates the collection tag (`'products'`), purging `/products` and all its query variants (`/products?category=Electronics`), while leaving individual product detail caches (`'product:1'`) intact.
- Updating product 1 (`PUT /products/1`) invalidates `'products'` and `'product:1'`, but **does not touch** `'product:10'` or unrelated resources like `'users'`.

## Complete Working Express Example

Below is a complete, runnable example demonstrating GET response caching, tag association, and mutation invalidation (`POST`, `PUT`, `PATCH`, `DELETE`):

```javascript
const express = require('express');
const cache = require('express-response-cache');

const app = express();
app.use(express.json());

// In-memory mock database
let items = [
  { id: 1, name: 'Mechanical Keyboard', price: 89.99 },
  { id: 2, name: 'Wireless Mouse', price: 49.99 },
];

// ----------------------------------------------------
// GET Routes: Cached with Resource Tags
// ----------------------------------------------------

// Cache items collection for 30 seconds
app.get(
  '/api/items',
  cache({ ttl: 30, tags: ['items'] }),
  (req, res) => {
    res.json({ success: true, data: items });
  }
);

// Cache item details for 60 seconds by dynamic tag
app.get(
  '/api/items/:id',
  cache({
    ttl: 60,
    tags: (req) => [`item:${req.params.id}`],
  }),
  (req, res) => {
    const item = items.find((i) => i.id === Number(req.params.id));
    if (!item) return res.status(404).json({ error: 'Item not found' });
    res.json({ success: true, data: item });
  }
);

// ----------------------------------------------------
// Mutation Routes: Automatic Invalidation
// ----------------------------------------------------

// POST: Create -> Invalidates 'items' collection
app.post(
  '/api/items',
  cache.invalidate({ tags: ['items'] }),
  (req, res) => {
    const newItem = { id: items.length + 1, ...req.body };
    items.push(newItem);
    res.status(201).json({ success: true, data: newItem });
  }
);

// PUT: Replace -> Invalidates 'items' collection and target 'item:<id>'
app.put(
  '/api/items/:id',
  cache.invalidate({
    tags: (req) => ['items', `item:${req.params.id}`],
  }),
  (req, res) => {
    const id = Number(req.params.id);
    const index = items.findIndex((i) => i.id === id);
    if (index === -1) return res.status(404).json({ error: 'Item not found' });
    items[index] = { id, ...req.body };
    res.status(200).json({ success: true, data: items[index] });
  }
);

// PATCH: Partial update -> Invalidates collection and target item
app.patch(
  '/api/items/:id',
  cache.invalidate({
    tags: (req) => ['items', `item:${req.params.id}`],
  }),
  (req, res) => {
    const id = Number(req.params.id);
    const item = items.find((i) => i.id === id);
    if (!item) return res.status(404).json({ error: 'Item not found' });
    Object.assign(item, req.body);
    res.status(200).json({ success: true, data: item });
  }
);

// DELETE: Remove -> Invalidates collection and target item
app.delete(
  '/api/items/:id',
  cache.invalidate({
    tags: (req) => ['items', `item:${req.params.id}`],
  }),
  (req, res) => {
    const id = Number(req.params.id);
    const index = items.findIndex((i) => i.id === id);
    if (index === -1) return res.status(404).json({ error: 'Item not found' });
    items.splice(index, 1);
    res.status(200).json({ success: true, message: 'Item deleted' });
  }
);

app.listen(3000, () => console.log('Listening on http://localhost:3000'));
```

## Error-Handling & Failed Mutation Protection

`express-response-cache` hooks into the final response `'finish'` lifecycle event and checks the actual HTTP status code:

- **HTTP 200–299 (Success)**: Invalidation occurs safely.
- **HTTP 4xx (Client Errors, e.g. 400 Bad Request, 404 Not Found)**: Invalidation is **skipped**; cached responses remain preserved.
- **HTTP 5xx (Server Errors)**: Invalidation is **skipped**.
- **Unhandled Exceptions / Connection Aborts**: Invalidation is **skipped**.
- **Safe Fallback**: Invalidation and caching logic are wrapped in error guards so cache errors never crash your Express application.

## Configuration Reference

### Caching Options: `cache(options)`

| Option | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `ttl` | `number` | `60` | Time to live in seconds. Must be a positive finite number. |
| `tags` | `string \| string[] \| Function` | `[]` | Resource tags to assign. Function signature: `(req) => string[]`. |
| `enabled` | `boolean` | `true` | Toggle caching dynamically. |
| `keyGenerator` | `Function` | `defaultKeyGenerator` | Custom function receiving `(req)` that returns a unique string key. |
| `store` | `CacheStore` | Default shared store | Custom `CacheStore` instance if isolating caches. |

### Invalidation Options: `cache.invalidate(options)`

| Option | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `tags` | `string \| string[] \| Function` | *(Required)* | Tags to invalidate. Function signature: `(req, res) => string[]`. |
| `methods` | `string[]` | `['POST', 'PUT', 'PATCH', 'DELETE']` | HTTP methods that trigger invalidation. |
| `enabled` | `boolean` | `true` | Toggle invalidation dynamically. |
| `store` | `CacheStore` | Default shared store | CacheStore instance to invalidate from. |

## Programmatic Cache API

If you need to manually clear caches, invalidate by tag, or inspect metadata outside route middleware:

```javascript
const cache = require('express-response-cache');

// Invalidate all entries tagged with 'products'
const removedCount = cache.invalidateByTag('products');

// Invalidate multiple tags at once
const totalRemoved = cache.invalidateTags(['products', 'categories']);

// Clear the entire default cache
cache.clear();
```

### Isolated Store Instances: `cache.createCache()`

For modular microservices, multi-tenant setups, or tests requiring completely isolated stores:

```javascript
const { createCache } = require('express-response-cache');

const { middleware, invalidate, store } = createCache({ ttl: 45 });

app.get('/reports', middleware({ tags: ['reports'] }), handler);
app.post('/reports', invalidate({ tags: ['reports'] }), handler);

// Retrieve entry metadata (timestamps and tags)
const meta = store.getMetadata('GET:/reports');
if (meta) {
  console.log(meta.key);        // 'GET:/reports'
  console.log(meta.createdAt);  // Epoch timestamp (ms)
  console.log(meta.expiresAt);  // Epoch timestamp (ms)
  console.log(meta.ttl);        // 45 (seconds)
  console.log(meta.tags);       // ['reports']
}

// Manual purge
store.invalidateByTag('reports');
```

## Known Limitations

- **In-Memory Single Process**: Caching and tag indexes reside in process memory. If running multiple clustered Node.js worker processes (e.g., PM2 cluster mode or multi-replica containers) without sticky sessions, each worker maintains its own independent in-memory cache.
- **Process Restarts**: Because entries reside in memory, restarting the Node.js process clears the cache.
- **Volatile Storage**: Not intended for persistent or distributed storage (like Redis or Memcached).
